# 云合企业级整改设计

> **状态说明（2026-07-18）：** 本文保留架构、安全与工程化整改建议；涉及产品业务范围时，已被 `2026-07-16-product-and-news-agent-design.md` 覆盖。特别是相册、照片文件、情感识别及旅行比较功能，不得按本文历史建议恢复或加固，应按产品设计和执行路线图执行下线。

**日期：** 2026-07-16  
**状态：** 已批准，待实施  
**范围：** 后端 FastAPI/Python、React 前端、CI/CD、工程规范

## 目标

在不重写产品功能的前提下，将项目从可演示的单体应用提升到可控的预生产基线：租户数据隔离可验证、文件访问受限、生产配置安全、质量检查不可绕过，并为后续架构演进建立可执行的边界。

本设计不把文件行数、框架名称或 DDD 目录命名当作目标。验收以可复现的安全测试、自动化质量门禁和部署行为为准。

## 非目标

- 本轮不迁移 SQLite 到其他数据库；是否迁移取决于并发、可用性和运维需求的单独决策。
- 本轮不重写 Agent、MCP 或 LLM 编排逻辑。
- 本轮不为追求“纯 DDD”进行无业务价值的大规模目录重排。
- 本轮不引入 Celery、Kafka 或微服务；异步任务的可靠性需求先被量化后再选型。

## 目标状态

```text
HTTP request
  -> authentication
  -> route-level identity extraction
  -> application authorization policy
  -> service/repository operation
  -> audited response

CI pull request
  -> backend lint + type check + tests + coverage threshold
  -> frontend lint + type check + production build
  -> security scan that fails on agreed severity
  -> required checks before merge
```

授权判断必须在应用服务或专用授权策略中统一执行；路由不得仅凭“用户已登录”就读取或修改带有 `user_id` 的资源。

## 阶段 0：立即风险封堵（P0）

完成期限：开始实施后的第一个发布批次。未完成前不得将服务暴露给不受信任用户。

### 0.1 相册与行程对象级授权

为每个相册操作建立同一个授权入口，例如 `AlbumAccessService.require_owned_itinerary(user_id, itinerary_id)` 和 `require_owned_photo(user_id, itinerary_id, photo_id)`。

该入口必须用于以下操作：

- 列出照片、标签、封面和 GPS 标记。
- 更新或删除照片。
- 设置封面。
- 生成游记。
- 上传照片。

`photo_id` 与 URL 中的 `itinerary_id` 必须同时匹配，且两者所属用户必须等于当前认证用户。对无权资源一律返回 404，避免泄漏资源存在性。不得把“行程没有 user_id”当作默认授权；遗留数据必须通过一次性迁移归属到明确账户，或在迁移完成前拒绝访问。

**验收：** 使用两个用户创建两个行程和照片；用户 A 对用户 B 的所有相册端点均返回 404，且不产生写入、外部 LLM 调用或审计成功事件。

### 0.2 文件服务目录边界

图片下载接口不得根据客户端提供的任意路径访问文件系统。接口只接收照片 ID 或数据库中已登记的不可猜测存储名；服务从数据库查询文件记录后再生成路径。

如保留路径参数，必须执行以下约束：

1. 使用 `Path.resolve()` 解析实际路径。
2. 验证解析结果位于 `data/album` 的解析根目录内。
3. 拒绝绝对路径、`..`、符号链接逃逸和非文件目标。
4. 验证路径与当前用户拥有的照片记录一致。

长期方案为短时效、单用途的图片签名 URL，令牌不放在 URL 查询参数中；在过渡期内，图片接口仍须验证当前会话或签名的照片权限。

**验收：** `../.env`、URL 编码路径穿越、绝对路径、符号链接目标全部返回 404；合法照片仅能由所有者取得。

### 0.3 调试端点隔离

生产环境默认不注册 `/debug` 路由。开发环境若保留，必须要求管理员角色，并对 `session_id` 执行所有权校验。MCP 配置、执行 trace、模型输入输出均视为敏感信息，不得被普通用户读取。

**验收：** 生产配置的 OpenAPI 中没有调试端点；开发配置的普通用户访问调试端点返回 403。

## 阶段 1：生产安全基线（P1）

### 1.1 配置分层与默认拒绝

建立 `development`、`test`、`production` 三套显式配置。生产配置必须在启动时校验：

- `log_level` 不是 DEBUG。
- CORS 只有显式 HTTPS 来源，禁止 `*` 与 credentials 同时使用。
- 未处理异常永不向客户端返回异常文本、调用栈或内部路径。
- Shell、任意 HTTP 出站和调试功能默认关闭；启用时需明确 allowlist 与审计。
- 必填密钥为空时服务拒绝启动，而不是静默降级。

安全响应头至少包含 CSP、`X-Content-Type-Options: nosniff`、`Referrer-Policy` 与按部署方式决定的 HSTS。所有生产日志采用结构化格式并对 token、密码、API key 和个人信息脱敏。

### 1.2 会话与令牌

令牌原文不得存入数据库。生成随机高熵令牌后，只存安全哈希和必要元数据（用户、过期时间、创建时间、撤销时间、可选设备标识）。验证时对提交令牌哈希查询。

Web 前端优先采用 `HttpOnly`、`Secure`、合适 `SameSite` 的 cookie；如果必须继续使用 Bearer token，需缩短有效期、支持刷新与旋转，并明确 XSS 防护责任。图片访问采用专用短期签名，不复用长期登录令牌。

**验收：** 数据库中不存在可直接复用的有效登录令牌；撤销后令牌立即失效；浏览器持久化存储中没有长期认证令牌。

### 1.3 限流与外部调用

限流中间件必须始终返回 `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`。生产环境 Redis 不可用时，应明确选择 fail-closed、限流容量降级或由网关接管，不能静默使用每进程计数器而误导为分布式限流。

LLM、地图、新闻和 MCP 外部调用必须有超时、最大重试次数、并发上限、目的地 allowlist 和可观测的失败指标。MCP 工具调用应按工具级权限授权，不得让模型文本直接扩大可执行范围。

## 阶段 2：不可绕过的质量门禁（P1）

CI 必须在每个 pull request 运行并作为分支保护的 required checks：

- 后端：Ruff、pytest、覆盖率阈值、mypy 或等价类型检查。
- 前端：ESLint、TypeScript 类型检查、Vite production build。
- 安全：Bandit、依赖漏洞扫描、密钥扫描；达到约定严重等级必须失败，禁止用 `|| echo` 吞掉结果。
- 测试不得以全局 `--ignore-glob` 跳过；临时隔离需有问题编号、到期日和单独的已知失败报告。

覆盖率仅作为防倒退底线，不作为安全保证。先为 P0/P1 资源授权、路径穿越、令牌撤销、CORS/生产启动校验建立测试，再逐步将后端总体覆盖率提升到 70% 以上。前端先消除现有 ESLint error，再将 lint 设为阻断项。

生产构建目前可完成，但入口 JS 过大。应对地图、相册、Agent 编辑器等重模块使用路由级动态导入；以初始 JS gzip 小于 150 kB 为首个性能预算，超限必须在 PR 说明中获批准。

## 阶段 3：架构与可维护性治理（P2）

先定义边界，再移动文件。保留当前单体部署，但引入以下可测试接口：

- `UserRepository`、`ItineraryRepository`、`PhotoRepository` 等领域需要的端口。
- `LLMClient`、`ToolExecutor`、`MCPClient` 等外部能力端口。
- `AuthorizationService` 和 `AuditService` 等应用服务。

`domain/` 逐步依赖这些抽象，而非直接导入 SQLite、OpenAI、MCP 具体实现；组合根负责将基础设施实现注入应用服务。优先改动正在修复的安全路径，禁止一次性全仓迁移。

文件大小规则改为告警指标而不是合并阻断条件。任何超过 400 行或圈复杂度超阈值的文件，需有负责人、拆分理由和日期化整改项；优先拆分 `domain/reasoning/engine.py`、数据库迁移与 MCP runtime 等高变更、高风险模块。

宽泛异常只允许出现在进程边界、后台任务监督器和外部集成适配器。每处必须记录错误类型、关联 ID、重试/降级行为，并保留原始异常链；业务层使用明确的领域或应用异常。

## 阶段 4：发布与运行治理（P2）

建立以下最小运维能力：

- 不可变依赖锁定和定期依赖更新；生成 SBOM。
- 数据库备份、恢复演练和迁移升级/降级演练。
- 健康检查区分存活、就绪、依赖状态；指标覆盖请求、错误、授权拒绝、限流、外部调用和后台任务。
- 结构化审计日志记录敏感写操作，但不记录令牌、密码、完整提示词或照片原始内容。
- 发布采用预发布环境、迁移预检、回滚策略和变更记录。

SQLite 可继续用于单节点、低并发场景；当出现多副本部署、写入锁竞争、RPO/RTO 或高可用要求时，再制定迁移到托管关系数据库的专项方案。

## 测试矩阵

| 场景 | 层级 | 必须验证的结果 |
| --- | --- | --- |
| 用户 A 读取或修改用户 B 的相册资源 | API 集成测试 | 404，无数据泄漏，无写入 |
| 路径穿越与符号链接 | API 集成测试 | 404，不访问根目录外文件 |
| 令牌撤销、过期、旋转 | 单元 + 集成测试 | 立即拒绝或按策略刷新 |
| 生产配置缺失/危险值 | 启动测试 | 启动失败且错误不泄漏密钥 |
| CORS 与安全响应头 | API 集成测试 | 仅允许配置来源，响应头完整 |
| Redis 与外部服务故障 | 集成测试 | 行为符合明确降级策略且有指标 |
| Agent/MCP 越权工具调用 | 单元 + 集成测试 | 被策略拒绝并产生审计事件 |
| 前端关键路由 | 构建 + E2E | 登录、资源隔离、图片访问可用 |

## 实施顺序与完成定义

1. 阶段 0 完成后才能进行任何公网或多用户测试。
2. 阶段 1 和 2 完成后才能进入预生产环境。
3. 阶段 3 和 4 可以持续迭代，但每个发布必须不降低阶段 0-2 的门禁。

一个阶段只有在代码、测试、CI 记录和部署配置均满足下列条件时才算完成：

- 对应验收测试在 CI 中通过。
- 安全扫描没有被静默忽略的高严重度结果。
- 文档中列出的生产默认值已实际生效。
- 变更经过独立审查，并附有回滚或降级说明。

## 对 AGENTS.md 的改造原则

将现有长文拆为两类文件：

- 根目录 `AGENTS.md`：不超过约 150 行，只放不可违反的安全规则、命令、目录边界、验收门禁和变更范围约束。
- `docs/standards/`：放 Python、Pydantic、迁移、命名和示例等参考材料，不以篇幅阻塞任务上下文。

规则必须可验证并与仓库现状一致。将“严禁 `except Exception`”“文件不得超过固定行数”等绝对表述改成有适用边界的规则；将对象级授权、路径安全、生产默认拒绝、CI 不可跳过和测试要求列为真正的硬性条款。每次修改规范都应同步调整自动化检查或明确人工审查责任。
